## Executive Conclusion

**有条件地推荐 GORM v2 + Goose + Koanf v2，采用少量明确的 Storage Service / Repository 与事务入口。** Gitea、Grafana、Casdoor 的源码主要使用 XORM，不能把它们当作 GORM 获得生产验证的证据。真正可借鉴的是多 Driver 配置、领域与存储边界、Migration 审核以及进程生命周期。对四个项目的源码结论置信度高，对此项目使用 GORM 能降低成本的推论置信度中等，尚未执行 PostgreSQL/MySQL PoC。

## Rejected Hypotheses

**被否定的推论**：“Gitea、Grafana、Casdoor 都使用 GORM，所以我们应复制 GORM”——它们的核对版本主要使用 XORM。“ORM 可代替事务/迁移”——Grafana 有 SQLStore 的事务接口及独立 Migration 管控，Gitea 处理 DB 差异。“Collector Confmap Watch 等于可直接下发 Agent 远程配置”——Collector 的本地组件配置处理与本平台 Release/OpAMP 控制面是不同系统边界。

## Remaining Unknowns

尚未在本项目运行 GORM PostgreSQL/MySQL 测试，故不宣称已满足 CAS、唯一性、事务发布、MySQL DDL 失败恢复以及连接池关闭等要求。将这些行为映射为 EP-001 的 P1 验收；若实际不满足，应回到 Research/Design 改选或采用局部 SQL。多租户身份/重复 UID 所有权依旧是 DD-001/EP-001 独立安全阻塞项。

## Options Comparison

| 候选 | 优势 | 主要风险 | 目前排序 |
|---|---|---|---|
| GORM + Goose + Koanf + 少量 Storage Service | CRUD 复用、可配置 PostgreSQL/MySQL、代码量较小 | SQL/CAS/模型兼容待真实验证 | 候选第一 |
| sqlc + PG/MySQL 双 SQL 与 Goose | 查询可预测、SQL 审核和精调方便 | 初始维护两套查询/生成代码 | 复杂查询出现时复评 |
| XORM + Migration | 三个上游项目存在相似模式 | 换 ORM 并不消除事务、迁移或领域分层成本 | 可行备选 |
| 全局 GORM / Handler 直接 CRUD | 初始代码少 | 生命周期和事务难管控；难测试 | 不建议 |

## Recommendation and Preconditions

当前建议 PR #2 保留 GORM v2、PostgreSQL/MySQL Dialector、Goose 与 Koanf。必须满足：Storage 的构造/Shutdown 显式控制；ORM Model 不流入 Registry/Policy/OpAMP；ConfigRelease 与 Assignment 共享同一事务；Assignment 使用显式条件 UPDATE、RowsAffected 和错误映射；生产 Schema 由 Goose 管理而非 AutoMigrate。**正式选择前**须在真实两库通过相同 Repository 合同测试并记录 Git revision、Migration 恢复证据，不能用开源案例代替 PoC。

## Handoff to ADR and ExecPlan

待纳入 DD-001/EP-001 的受验证约束：一部署一种主数据库，Driver 可配置但不自动迁移已有数据；Storage Service 通过业务 Repository / UnitOfWork 暴露需要的操作，避免“每表一接口”；GORM 不替代身份边界、CAS 和事务；Goose 单独执行生产迁移，MySQL DDL 隐式提交须有恢复策略；Go 组件需显式创建/关闭。以上是**推荐输入**，尚未批准。源码永久链接由 notes/opensource-comparison.md 拥有；双数据库 PoC 属 EP-001；长效架构决定需由 Design/ADR Owner 明确授权。
